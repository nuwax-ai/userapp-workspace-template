# 部署、发布与回滚

这篇讲:你的代码构建后长什么样、点「发布」之后平台做了什么、怎么回滚、版本保留策略、数据库迁移
约定、健康检查,以及发布失败时怎么排查。

> 日常发布在**平台界面点「发布」按钮**即可,一键完成。这篇帮你理解中间发生了什么,以及出问题时该看哪。

---

## 1. 构建产物长什么样

构建成功后,平台产出**一个不可变的发布包**:

```
workspace-package-<release_id>.zip
├── workspace.manifest.toml        ← 你的 workspace manifest(原样打入)
├── release.lock.toml              ← 平台生成的不可变运行时快照
├── database/                      ← workspace 根 SQL(activate 后平台自动执行)
├── pingap/                        ← 仅 extend/custom 模式存在
└── <各 service 目录>/             ← 各服务的构建产物 + {目录}/database/*.sql(原样打入)
```

发布包按声明收集制品,不会自动复制全部源码。已有 monorepo 的服务产物须包含运行所需的共享模块
和依赖,能在隔离于原源码的目录中运行。构建脚本可调用原根构建,再把产物收集到一级服务目录；
详见 [已有项目接入指引](07-import-existing-project.md)。

### `release.lock.toml` —— 发布的运行时权威

平台构建时生成,锁定这次发布的**全部运行时事实**:

- release ID;
- 各 service 的稳定身份(`service_id`)、目录、依赖拓扑顺序;
- 各 service 的**确定性端口**(4000–7999 范围内,由 service 集合确定性推导);
- enabled 状态、run/migrate/health/proxy/logs/env;
- Pingap 模式 + 精确版本/commit;
- 平台运行时版本约束与版本化镜像引用(启动时复核)。

应用启动时**只读 release.lock.toml**,不再重新扫描源 manifest、不再重新推导端口和顺序。启动时还会
复核 release lock——任何不一致,应用保持 not-ready。

> 你不需要手写 release.lock.toml,它是构建时自动生成的。但排错时(端口、启动顺序对不上)可以在
> 实际部署 workspace 中查看 `release.lock.toml`，不要假定所有容器都使用 `/app/code`。

## 2. 发布结果与业务就绪分开观察

RCoder 的操作结果、app-cli 的制品部署段和业务就绪不是同一个状态。按本次 operation ID
读取平台状态；排查容器内编排时查看 app-cli 的部署状态和运行时状态，不根据界面提示推断已经回滚。

| 观察面 | 含义 |
|---|---|
| 制品部署段 `deploy_stage` | `pending/succeeded/failed`；`succeeded` 说明制品激活完成，不代表服务已 Ready |
| app-cli `phase` | `idle/deploying/orchestrating/running/failed`；反映容器内编排阶段 |
| 业务就绪 `data.ready` | 只读查询当前 web 服务和入口是否可用；不启动或唤醒服务 |
| 平台操作与恢复结果 | 表明本次操作是否完成、失败或需要继续恢复；保留 operation ID 和具体错误 |

```
构建发布包 ──► 下载校验/切换代码 ──► 服务编排 ──► 查询业务就绪
                                      │
                                      └─► 失败/结果未知：读取错误和恢复状态
```

## 3. 发布的三个逻辑阶段

下面描述逻辑步骤，不是要求应用调用三个独立的 prepare/activate/confirm 接口。
当前 RCoder 将制品交给容器内 app-cli 完成部署与编排。

### 阶段一:下载与校验

下载发布包 → 校验大小、SHA-256、zip 完整性 → 校验包根有 `release.lock.toml` 且 release ID 匹配
→ 准备本次部署的候选目录。

这一步出问题通常是下载失败、包损坏、校验不匹配或 release.lock 缺失。先查看具体错误再修复。

### 阶段二:激活与编排

把发布包解压到临时目录并完整校验 → 若旧版本在跑,先停整个 workspace → 当前代码移到回滚备份
→ 新代码切到实际部署目录 → 按运行环境策略等待 PG、执行迁移并启动服务。

> 整组切换会有服务中断，时长受迁移、构建产物及服务启动影响。制品部署段先完成、业务仍启动中是合法状态。

### 阶段三:核验实际结果

结合操作状态与业务就绪查询(见 [§7 健康检查](#7-健康检查))：

- **就绪**：核对当前版本与入口，验证实际页面/API；
- **明确启动失败**：读取服务与阶段错误。新代码可能已经激活，不能认定旧版本正在运行；
- **结果未知或需要恢复**：使用平台支持的恢复入口继续原操作，不删除 journal、清锁或换身份盲目重试；
- **仍启动中**：等待当前操作，不能把查询等待超时当作确定失败或已完成回滚。

> `failed` 不承诺自动回滚。即使已确认旧代码恢复，也不代表数据库迁移已撤销。

## 4. 回滚

**回滚 = 使用可用的历史制品重新部署。** 通过平台提供的历史版本入口发起，底层仍执行制品校验、
切换和编排；不依赖手工移动容器内目录。存在结果未知的原操作时，先完成其恢复核验。

```
当前 v3(有问题)
   │  通过平台选择 v2 制品重新部署
   ▼
v2 校验/激活 → 服务编排 → 确认当前版本与业务就绪
```

> ⚠️ **回滚不执行数据库 down migration。** 代码回到旧版本,但数据库 schema 不会回退。所以你的迁移
> 必须保证:新旧代码短时间内都能兼容同一套 schema(见下一节)。

---

## 5. 版本保留

历史制品的可用范围与保留策略以平台版本管理为准，应用模板不控制保留数量。
回滚前确认历史制品仍可获取。容器内的备份目录、journal 和工作区不是可随意清理的历史版本仓库；
不要通过删除它们解决启动失败。

---

## 6. 数据库迁移约定(重要)

`run.migrate` 在服务启动**前**、按依赖拓扑顺序执行。**任何**一个 service 的 migration 失败,整个
workspace 启动失败。

你的迁移脚本必须遵守:

1. **可重复执行(幂等)**——migrate 可能因回滚后重启、重试而多次跑,重复执行不能报错;
2. **新旧代码短期都能兼容同一 schema**——回滚时代码退回旧版,但 schema 不退,旧代码得能跑在新 schema 上;
3. **先 expand,再发代码,最后 contract**——加列先加(兼容旧代码),删列要等旧代码下线后再删;
4. **平台不执行 down migration**——别指望回滚自动改库。

### `database/` 目录 —— 平台自动执行的 SQL(与 run.migrate 互补)

workspace 根 `database/` 与各子项目 `{目录}/database/` 下的 `.sql` 文件,在发布 **activate 成功后**
由平台按序自动执行(容器内 psql):根 `database/` 先执行,子项目按目录名字典序,目录内按文件名字典序。

与 `run.migrate` 的分工:**建库/扩展/平台侧初始化**类 SQL 放 `database/` 目录(平台执行,
单文件失败仅日志、不阻断发布);**应用自身的 schema 迁移**走 `run.migrate`(失败阻断启动)。

关键约束(完整规则见各 workspace 的 `database/README.md`):

- **幂等**——每次发布都会重跑全部 SQL(无执行记录),必须 `IF NOT EXISTS` / `ON CONFLICT` 自带幂等;
- **文件名只能用 `[A-Za-z0-9._-]`**——中文/空格等字符的文件名会被平台静默跳过;
- **只扫 `database/` 直接子层**——子目录不递归,非 `.sql` 文件不进发布包;
- **开发阶段不自动执行**——本地调试时 schema 变更需手动执行(dbx / psql)后再放入本目录。
- **遇错停止不等于回滚**——`ON_ERROR_STOP=on` 中止当前文件，先前已提交语句可能保留。
  要求原子性的 SQL 显式设计事务；建库等不能放入事务的命令单独处理。

## 7. 健康检查

以下为服务健康路径声明,不是三套已装配的容器探针。未声明 startup_probe 时 builtin 对 dev + devrun 做 TCP 检查,对其他进程做 `readiness_path` HTTP 2xx 检查；supervisord 使用进程启动确认及可选 workspace bridge。HTTP worker 仍须保留模板的健康服务,不能因无公开路由就删除监听。显式 process worker 使用 app-cli >= 0.3.9 的启动检查，见 [worker 模式](08-worker.md)。

| 字段 | 默认路径 | 当前作用 |
|---|---|---|
| **startup**(启动) | `/health` | 启动健康路径声明,不取代上述实际检查路径 |
| **readiness**(就绪) | `/health` | 供对应启动检查、web 业务就绪查询及显式 bridge 使用；查询本身不改运行状态 |
| **liveness**(存活) | `/health` | 存活探针声明(不等于"失败即重启容器"——是否装配容器级探针由平台运行时配置决定) |

在 `project.manifest.toml` 的 `[health]` 里改:

```toml
[health]
startup_path = "/health"
readiness_path = "/ready"      # 建议 readiness 做更深的检查(含 DB 等依赖)
liveness_path = "/health"
```

**建议**:`readiness` 廉价、只读地覆盖数据库等必需依赖,连接失败返回非 2xx；`liveness` 只反映进程自身。不能依赖这些声明自动重启容器,也不能将一次业务就绪查询当成启动、唤醒或摘流命令。

### workspace 级就绪桥接(可选)

app-cli 的 `/health` 表示管理进程存活；`/ready` 根据编排阶段及可选 bridge 返回结果。
业务启动失败不等于管理进程退出。业务可访问性用独立只读接口查询，HTTP 200 表示查询完成，
响应中的 `data.ready` 才表示业务就绪；不能将管理探针与业务状态混为一谈。

若想让"某个后端就绪 = 整个应用就绪",在 `workspace.manifest.toml` 配:

```toml
[health]
bridge_service = "api"       # 填某个 service_id
```

该声明让 app-cli `/ready` 的判断参考此服务的 `readiness_path`。是否影响容器 Ready 和入口流量，
取决于部署是否把这个端点接入容器探针；manifest 本身不执行摘流或重启。`/health` 仍独立于业务健康。

## 8. 优雅关闭

停服务时,平台向每个服务的进程组发 `SIGTERM`,等待该服务声明的 `run.shutdown_timeout_seconds`
(默认 30 秒),超时才 `SIGKILL`。

```toml
[run]
command = ["./server"]
shutdown_timeout_seconds = 30   # 给服务多久优雅退出
```

你的服务应该:收到 `SIGTERM` 后停止接新请求、处理完在途请求、关闭数据库连接、退出。需要更长时间
(比如等长任务)就调大这个值(必须 `> 0`)。

---

## 9. 闲置回收与流量唤醒

平台可回收长时间空闲应用的计算资源，保留其持久卷。进程内状态和未写入持久目录的文件不受此保证；
应用应把需要跨重启保留的数据写入配置的持久目录。

- **回收后下次有请求来**,平台自动把它唤醒(扩回 1 副本,等就绪后代理),首次请求会多等几秒到几十秒;
- **付费/不希望被回收**的应用,可由平台侧设置为永不回收;
- 回收策略由平台/计费侧统一管理,普通开发者一般不用关心。

这是平台层的资源管理。应用按对应探测策略启动，迁移保持幂等；worker 的在途任务还需自行处理关闭、重启后的重试与去重。

## 10. 常见发布错误排查

| 现象 | 可能原因 | 怎么查/怎么改 |
|---|---|---|
| 构建阶段就失败 | manifest 校验不过 / build.command 报错 / 没产出 artifact | 看界面构建进度里哪个 service 失败及报错;本地先跑一遍 build 脚本;对照 [字段参考 §校验规则](03-manifest-reference.md#四校验规则完整清单) |
| `release version not supported` / 工具链版本不够 | 构建镜像的工具链版本低于项目要求(如 Java 25 项目跑在 Java 17 镜像) | 降项目的目标版本,或等平台升级构建镜像 |
| 激活后业务不 Ready / 启动失败 | 探测配置不对 / 进程退出 / HTTP 服务端口不对 / DB 连不上 | 查本次操作状态、服务日志和实际版本；按 HTTP/TCP/process 策略核验，不假定已回滚 |
| readiness 一直不就绪 | readiness 检查的必要依赖未就绪 | 分别查询进程存活与依赖状态；修复实际依赖，不改成恒成功来掩盖故障 |
| 服务能起但外部访问 502/404 | `[proxy].path` 没配 / 配错 / 服务没监听 `$PORT` | 看 [反向代理与路由](04-pingap-routing.md);确认 path 拼写;用日志面板确认服务收到了请求 |
| 日志面板查不到应用日志 | `[[logs.sources]].glob` 没匹配上实际文件名 / 日志没写到 `$APP_LOG_DIR` | 检查 glob 和应用写文件的路径;若声明了匹配 stdout 的 source(如 `runtime`),先看它定位启动报错 |
| 回滚后服务报错 | 迁移非幂等 / 新 schema 旧代码不兼容 | 修迁移脚本(幂等 + expand/contract);见 [§6](#6-数据库迁移约定重要) |

## 11. 界面操作速查

| 想做什么 | 在界面上 |
|---|---|
| 把代码部署上线 | 应用页点「发布」(构建 → 准备 → 激活 → 确认,一键) |
| 只验证构建、不部署 | 点「构建」 |
| 看发布进度 | 发布时的进度面板(每个 service 的构建状态 + 激活/确认阶段) |
| 回滚到旧版本 | 「版本列表」里选历史版本点「回滚」 |
| 查看历史版本 | 「版本列表」(显示状态、时间;当前版本受保护不可删) |
| 停止 / 启动 / 重启应用 | 应用页的「停止」「启动」「重启」按钮(操作整个 workspace) |
| 看日志 | 「日志」面板(按 service / source / 级别 / 关键词 / 时间过滤) |
| 接入已有项目 | 手动导入代码后,请 agent 按 [接入指引](07-import-existing-project.md) 适配；实际导入入口以平台支持为准,不依赖自动 detect 或确认界面 |
